# Architecture

The gateway verifies provider HMACs against the exact HTTP body and commits an inbox event before returning 202. It never calls a carrier or Slack on the delivery path. The inbox dispatcher leases rows with `FOR UPDATE SKIP LOCKED`, sends authenticated references to the appropriate n8n provider workflow and checks durable completion. Crashed leases become eligible for retry. Ten failed attempts move an event to the dead letter state.

Each provider workflow invokes the shared processing workflow. Its connected stages invoke reusable normalization, cancellation, allocation, shipping and reorder workflows. Dedicated TypeScript endpoints own SQL transactions; n8n owns orchestration, schedules, error handling and execution visibility. PostgreSQL is the business system of record. Redis transports n8n queue jobs between the main instance and workers; losing Redis does not lose the inbox. Redis AOF and PostgreSQL volumes are persistent.

## Consistency and inventory ownership

Order preparation serializes by `(store, external order)` using a PostgreSQL advisory transaction lock, followed by an order row lock. Every mutation checks that the event still owns the order's current revision. Older source timestamps are ignored. Equal timestamps allow payment or terminal-state precedence; equal-rank ambiguous line changes are quarantined. Terminal orders never reopen automatically. Changes after actual fulfillment require operations review, not automatic restocking.

Inventory operations lock the order first and all affected balances in `(product_id, warehouse_id)` order. Allocation computes `max(0, on_hand - reserved - safety_stock)`. Incoming units contribute to replenishment projection but cannot be sold before receipt. Duplicate SKUs are aggregated by canonical product, including store aliases. Warehouses must support the destination country; matching destination state is preferred, then warehouse priority. Unknown SKUs produce shortages. An all-or-nothing store gets no reservations unless every line can be allocated. A configured partial store can reserve available lines and requires manual review before fulfillment.

**The operational PostgreSQL database owns stock and reservations.** A live installation must route every writer/reservation through this authority, or replace allocation/release/fulfillment with an authoritative external inventory API. The read-only snapshot adapter is NOT an external reservation API. This project does not claim to prevent overselling by unrelated systems that write their own stock. Warehouse `source` must remain `local-postgres` for this implementation. Production activation requires verifying exclusive inventory ownership.

Confirmed reservations expire after 30 minutes by default, including paid orders awaiting operations. The expiry job releases the whole unfulfilled order, changes it to BACKORDERED and alerts operations. It never leaves a stale READY_FOR_FULFILLMENT order with expired stock. Cancellation releases confirmed/held stock once. Provider-confirmed fulfillment consumes reserved and on-hand units. Partial provider fulfillment is routed for manual inventory review because line-level fulfillment IDs require a store-specific adapter. Its stock stays blocked even after expiry; later cancellation or quantity changes are quarantined so already shipped units cannot return to available stock. Matching full provider fulfillment can consume that allocation; other corrections require reviewed inventory accounting.

## Side effects and failures

Rate lookup holds the order lock so cancellation cannot invalidate an in-flight quote commit. Packing is configured as individual parcels or bounded vertical SKU stacks. No label-purchase endpoint exists. Quote failure keeps stock reserved until retry or expiry, and enqueues an operations alert. Network calls have bounded timeouts and retry transient/429 responses with backoff and jitter. Each successful stage is safe to replay. No mock fallback exists in LIVE_MODE.

Slack notifications use a durable outbox with a unique semantic key, retry leases and bounded attempts. Up to ten alerts flush in a batch; category, severity and correlation appear in Block Kit. Slack delivery is at least once: a crash after Slack accepts a request but before the database commit can duplicate a message. `client_msg_id` is provided, but production exactly-once delivery is not assumed. Unresolved reorder alerts share one record and notification. No purchase orders are issued.

Reconciliation uses paginated read-only store APIs with a five-minute overlap and persisted per-store watermark. Initial live lookback is 60 days and depends on Shopify order access scope. A >250-line Shopify order stops that store's scan for manual bulk handling rather than silently truncating. Local mock stock is authoritative; divergent injected snapshots produce review alerts. Live snapshots can update on-hand/incoming only when the source timestamp is newer and the count supports existing reservations plus safety stock. Unknown mappings, source failures, unsafe counts and stuck orders alert operators.

The customer payload is stored only in the protected database. Logs and notifications carry operational IDs, not names, addresses or emails. Set a data retention policy before production.
